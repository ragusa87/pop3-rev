# Original game spec from the exe

Goal: answer "how does the original do X" from the executable, record it as an implementable spec in
`/home/laurent/compile/open-populous/docs/specs/pop3-rev-analysis.md`, and turn every difference with our
implementation into a `TODO.md` item.

## Paths
- Exe (Direct3D build, the only one the addresses fit): `~/.wine/drive_c/Program Files (x86)/Bullfrog/Populous - A l'aube de la création/D3DPOPTB.EXE`.
  Every address in the skill, the Ghidra export and the spec is a `D3DPOPTB.EXE` address.
- `POPTB.EXE` (software build, same release): same game code, different link order. Use it only for live
  measurements when it runs better; never analyse its disassembly. `pop3-rev/docs/poptb_map.tsv` maps D3D to
  POPTB addresses (`code`: matched functions; `data`: globals, `votes` = matched references, trust ≥ 2),
  regenerated by `python3 scripts/poptb_map.py D3DPOPTB.EXE POPTB.EXE docs/poptb_map.tsv`. Shifts: game state
  0x87CBD0..0x98489C −0x17A68 (turn, tribes, unit pool and pointers, rng); per-type tables −0x7220; sin/cos
  −0x31748; code has no single shift (look the function up).
- Ghidra export (names are a previous analyst's guesses, often wrong or shifted): `pop3-rev/backup/backup.xml`.
- Spec to write: `open-populous/docs/specs/pop3-rev-analysis.md`. Our specs: `open-populous/docs/specs/*.md`.
  Our backlog: `open-populous/TODO.md`.

## Setup (once per session)
`bash .claude/skills/original-game-spec/scripts/setup.sh` builds in `$WORK` (default `/tmp/pop3-spec`, or the
session scratchpad: `WORK=<scratchpad> bash ...`):
- `dis.txt`: full intel-syntax disassembly;
- `fn.tsv`: Ghidra functions (start, end, name);
- `consts.txt`: the exe's 340 named tuning constants (name, size, flags, address, exe default);
- `constant.txt`: the decoded shipped `levels/constant.dat` (its values override the exe defaults at run time).

Tools:
- `python3 scripts/sl.py LO [HI]`: disassembly of a range (one function if HI is omitted);
  `python3 scripts/sl.py fn ADDR...`: which Ghidra function holds an address.
- `grep` on `dis.txt` for an address (`0x5aa510`), a field (`+0x955\]`) or a call (`call   0x4ed8a0`).
- `scripts/livemem.py ADDR:FMT[:LABEL]... [--every 0.25]`: read the running game's memory. Wine maps the exe at
  0x400000, so virtual addresses work as they are. Always pass D3D addresses: with `POPTB.EXE` running they are
  translated through `scripts/addrmap.py` (exact match, else the shift of the closest mapped global below, which
  covers struct fields); pointers read from memory are live addresses and need no translation. The user must run
  it with sudo (`ptrace_scope` 1 and Wine re-parents the game): give them the exact `! sudo python3 ...` command,
  with the game started as `wine D3DPOPTB.EXE` (or `wine POPTB.EXE`) in a level. Write a dedicated watcher
  script in the scratchpad when a value must be
  followed per turn (poll the turn counter, snapshot on change).

## Method
0. If `pop3-rev/docs/functions.tsv` already has rows for the relevant functions (built by the
   `exe-function-map` skill), skim them for a head start.
1. **Find the code**: start from what is named.
   - A constant: `grep -i NAME consts.txt` gives its address; grep that address (or a per-type table base plus
     the field offset) in `dis.txt`.
   - Per-type tables are read as `[type*stride + base + field]`; compute the base and grep it.
   - A Ghidra name: `grep -i name fn.tsv`, then verify what the code really does.
   - A unit kind: allocations are `alloc_unit(class, type, tribe, pos*)` = `call 0x4ed8a0` with pushes in
     reverse; per-class init/per-turn handlers switch on type (+0x2B) or state (+0x2C) through jump tables:
     read the table with python from the exe bytes.
   - When static search stalls, measure it live.
2. **Read it**: follow the data flow until the rule can be written as pseudocode with exact numbers. Note the
   rhythm (`test [unit+0x2e],N` = every N+1 turns, the turn counter 0x89D188), the units (world units: 512 per
   cell; heights 0..1024; angles 2048 per turn; percents stored ×256/100), and file vs exe values.
3. **Check**: a second look at the branch conditions; for anything timing- or value-critical, a live
   measurement. Mark what is inferred `(unverified)`; never present a guess as traced.
4. **Delegate wide sweeps**: for many independent topics (all spells, all buildings), write a context file
   (paths, tools, engine facts, maps already known, report format) and run parallel agents, then reconcile
   their reports (they contradict each other on details: re-check those).

## Engine facts already established (verify before relying on new ones)
- 12 game turns per second (measured), fixed 83 ms step. Our simulation runs 10 ticks per second.
- Unit record 0xB3 bytes, pool of 2000 at 0x8E0428, pointers at 0x890390; class +0x2A, type +0x2B, state +0x2C,
  sub-state +0x2D, class_counter +0x2E, tribe +0x2F, movement profile +0x30, pos +0x3D (x, z, height).
- Tribes at 0x89D1C8, 0xC65 bytes each; player tribe index 0x89C6F0.
- Constant table at 0x5AA60F (31-byte records); per-type tables: persons 0x5A7060/0x32, buildings 0x5A7228/0x4C,
  scenery 0x5A79B0/0x18, spells 0x5A80D0/0x3E, movement profiles 0x5A7B90/0x1A, vehicles 0x5A7938/0x17.
- Pseudo-random 0x89D178: `x = ror(x * 0x9E3D + 0x24DF, 13)`. Sin/cos tables 0x5DDDE8 / 0x5DE5E8 (16.16).
- Effects (class 7): init table 0x50A59C by type, per-turn table 0x50AFD4 by state; `0x401B10(unit, state)`.
- Everything else already found is in pop3-rev-analysis.md "Reference": read it before searching.

## Writing the spec (pop3-rev-analysis.md)
Re-read the file first (the user edits it), and fit into its structure:
- **Takeaways**: one bold line per major finding, with a pointer to its section.
- **A rules section** (`## Topic [exe]`, `[exe, measured]` when confirmed live): pseudocode in a `text` block,
  tables of values (exe default and file value), times in turns and seconds, worked examples marked as estimates
  when not measured.
- **Impact on our specs**: one bullet per difference, naming our spec/code (`units.md`, `game_core::...`) and
  the original's value next to ours, with the conversion to our ticks when relevant.
- **Open questions**: what was not traced; remove the ones now answered.
- **Reference**: functions (address, name or proposed "rename", one-line role), unit/tribe fields, table fields.
Style: the file's own (lines ≤ 115 characters except table rows, no Markdown bold inside tables except where the
file already does, `code` for names and fields).

## Writing back to pop3-rev/docs/functions.tsv
For every function address you add or update in the spec's Reference table this session, also append or update
the matching row in `pop3-rev/docs/functions.tsv` (same file `exe-function-map` writes; re-read it first, it's
append-only but may have changed). Columns: `address name feature_area status role` — see
`.claude/skills/exe-function-map/SKILL.md` for the exact conventions (lowercase `0x...` address, `feature_area`
restricted to its fixed list, `status` named/traced/verified, `role` a single self-contained line). This keeps
`functions.tsv` the superset of every function either skill has looked at, without a separate catalog-only
session. Sort by address when done (`sort -t$'\t' -k1,1`).

  the analysis file, which is the addressable reference.
